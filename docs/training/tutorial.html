Track A · PRD §2.2

Template Designer / Business Analyst

You own the look, logic, and lifecycle of every template. Your pain today is rigid desktop tooling and the impossibility of testing print and digital at the same time; NextGen-CCM's answer is one web designer producing one Unified Document Model rendered to every channel.

Needs (from the PRD)

  • Intuitive web interface for templates and personalization logic
  • Version management and staging tests
  • One design, tested across physical and digital formats

Pain points this track removes

  • Rigid desktop design applications
  • Complex migration scripts
  • Look-and-feel drift between print and digital output

Learning path: Modules 01 → 02 → 03 → 04 → 08 → 10 → 13 → 14 (Implementation Consultant path). This track drills modules 02 (template design) and 08 (business rules).

Tour the Designer and read a template FR-1.1 FR-1.2

Open Designer and click Edit on Customer Invoice. The top table lists every template with its application, version, and approval status; the editor below shows the template definition — in the MVP, raw UDM JSON (the full product adds the WYSIWYG surface on top of this same model):

{
  "id": "tpl_invoice",

                 "key": "{{product_code}}" } ],                    ← FR-3.4
  "blocks": [
    { "id": "header",   "locked": true,  "text": "ACME CORP — INVOICE" },
    { "id": "greeting", "editable": true, "text": "Hello {{name}}, " },
    { "id": "body",     "editable": true,
      "text": "Your invoice {{invoice_number}} for plan \"{{lookup.product.title}}\" …" },
    { "id": "promo",    "rule": { "field": "lookup.product.promo", "op": "exists" },
      "text": "Special offer: {{lookup.product.promo}}" },

This single object is the UDM source (FR-1.2): the composition engine merges it with a payload and renders the same model to PDF, email, and SMS. Print and digital cannot drift, because there is nothing separate to drift.

A4

Theme, watermark & page setup FR-1.6 FR-1.7 FR-4.4

Three production-print controls live right in the template definition you just edited:

  • Theme (themeId, FR-1.6): typography, colors, header/footer structure come from theme_brand. Templates subscribe; a rebrand is one theme edit propagated through version control, not two hundred template edits.
  • Watermark (FR-1.7): "watermark": null in production; previews of unapproved versions are stamped DRAFT automatically. Click Preview PDF (DRAFT watermark) on your v3 draft to see it. Convention: DRAFT on non-production previews, COPY on reprints, nothing on production.
  • Page setup (FR-4.4): size: A4, orientation: portrait, duplex: true — plus nUp, which scenario A7 puts to real use.
A5

The invoice carries two live rules, and you already read them in A1: ca_notice renders only when state == "CA", and promo renders only when the product lookup returned a promo. Rules support eq / ne / gt / lt / in / exists and live outside the layout, so an analyst changes logic without touching design.

A6

Reference-data lookups FR-3.4

The invoice never hard-codes plan names. Its lookups entry keys products.json by the payload's product_code, and blocks reference the result as {{lookup.product.title}}. The real reference store:

// backend/samples/products.json — a reference source (file, table, or REST in the full product)
{
  "GOLD-01": { "title": "Gold Cloud Plan",   "promo": "Upgrade to Platinum for 10% off …" },
  "SILV-01": { "title": "Silver Cloud Plan", "promo": "Add Premium Analytics for $9/mo." },
  "BASE-01": { "title": "Basic Plan" }        ← no promo → the promo rule (A5) suppresses the block
}

Note the interplay: BASE-01 has no promo key, so the exists rule from A5 drops the offer block for Basic customers. Lookup + rule together implement "show rate-table/marketing content per product" with zero template branching. Lookup results are cacheable per batch run for throughput.

A8

Conversational AI edit FR-7.4

In the Designer's AI box, type: "make the greeting bold and move the promo above the body", then click ✨ AI Edit. Three guarantees make this safe for regulated content:

  • The instruction becomes structured block edits on the UDM — not free-form generated markup. Invalid or unknown edits are skipped and reported back to you.
  • Locked blocks are re-enforced server-side — the response lists any skipped edits with the reason (locked).
  • The result is saved as a new draft version requiring re-approval, attributed in version history (FR-1.4). The UI says exactly that: "Saved as new draft version v4 — approve to publish."

(Requires OPENROUTER_API_KEY; without it the endpoint answers 503 with a clear message and you narrate this scenario instead.)

A9

Approve — and prove the gate FR-1.5

Before approving, go to the Dashboard and try to send using your draft — the API answers 409 Conflict: drafts cannot reach a customer (the smoke suite asserts this exact behavior). Click Approve (FR-1.5) in the Designer, send again, and it flows. In the full product this gate is a configurable multi-stage serial/parallel reviewer chain; the MVP's single draft→approved transition sits at the identical enforcement point.

Knowledge check — Track A

Answer before expanding.
1. A client wants the email disclaimer shorter than the print disclaimer. What do you tell them?

Both channels render from the same UDM (FR-1.2), so one disclaimer block feeds both. The right mechanism is a conditional rule (FR-8.1) or a channel-specific block variant — never two divergent templates. If it is a locked regulatory block (FR-1.3), the change also needs the designer/compliance unlock permission you saw in A3.

2. Basic-plan customers must never see promotional copy. Where is that enforced in the invoice template?

Nowhere in the layout — it falls out of A5 + A6: the promo block's rule is lookup.product.promo exists, and BASE-01 in the reference store has no promo key. Change the reference data and behavior changes portfolio-wide, with no template edit.

3. What state is a template in immediately after an AI Edit, and why does it matter?

A new draft version requiring re-approval (you saw the literal message in A8). AI-assisted edits never shortcut governance: same version history, same approval gate as a human edit.

4. The print shop asks for the business cards "stack-cut ordered." Which FR are they invoking?

FR-4.4 — N-up imposition's record-sequence ordering (stack-cut vs. row-major), alongside grid, gutters, and cut marks. The MVP demonstrates the 10-up grid and cut marks; ordering options are full-product scope.

B6

Lifecycle hooks: fix data before it enters the pipeline FR-13.1 FR-13.2

Why did jane doe and JOHN SMITH print as Jane Doe and John Smith in B4's report? A pre-ingestion hook — sandboxed JavaScript (Node vm, 500 ms CPU quota) registered against the pipeline stage. The real seeded hook:

// data/hooks.json — hook_normalize_names, stage: "pre_ingestion", applicationId: "*"
// Normalize driver-file records: trim + title-case names (FR-13.2 demo)
if (ctx.data && Array.isArray(ctx.data.records)) {
  ctx.data.records = ctx.data.records.map(r => ({
    ...r,
    name: r.name ? String(r.name).trim()
      .replace(/\w\S*/g, t => t[0].toUpperCase() + t.slice(1).toLowerCase()) : r.name,
  }));
  log('normalized ' + ctx.data.records.length + ' records');
}

Hooks exist pre/post at every stage — ingestion, lookup, composition, rendering, post-processing, dispatch, archiving — are versioned per application (FR-14.1), and emit their own audit/log events. Common patterns:

StagePre-hook examplePost-hook example
Ingestionnormalize / validate driver record (above)reject-and-report malformed rows
Reference lookuprewrite lookup keycache or enrich the result
Composition / renderinginject computed fieldsstamp job metadata
Delivery dispatchfinal suppression check (do-not-contact)notify a downstream system
Archivingadd index fieldstrigger retention workflow
B7

Turn up logging on one job only FR-6.4

Log verbosity (trace / debug / info / warn / error) is runtime-switchable with no restart — globally and per scope. The support pattern: production stays at info; when one batch misbehaves, raise only that job's scope, capture, drop it back:

# global stays at info; one failing job goes to trace
curl -s -X POST http://localhost:3000/api/v1/admin/log-level \
  -H "Content-Type: application/json" -d '{ "level": "trace", "scope": "job:job_a18571b5c8" }'

The Dashboard's Log Level card is the same call. The smoke suite verifies both the global and per-scope switch.

B8

Status-code catalog & ops runbook

Every deliberate rejection you will meet in this tutorial, in one table — wire these into your client library's error handling:

CodeWhenMeaning / correct reaction
202on-demand acceptedNew work queued; store the transaction_id.
200replayed idempotency key (B2)Original transaction returned, replayed: true — do not treat as a new send.
201batch / reprint created (B4, B5)Job accepted; report file path in the response.
403locked-block change (A3)Content governance, not auth failure — route the change to a privileged designer.
409send with unapproved template (A9)Approval gate — approve the draft or pin the last approved version.
503/api/v1/ai/* without API keyAI features disabled by configuration; everything else unaffected.
404unknown template / transaction / jobCheck the ID; templates are application-scoped (FR-14.1).
  • Secrets in backend/.env (git-ignored); settings (port, corsOrigin, AI model, storage paths, log level) in backend/config.xml. Precedence: env var → config.xml → default. Never put secrets in config.xml.
  • Frontend wiring: frontend/config.js sets window.CCM_API_BASE; the backend's <corsOrigin> must match the frontend origin in production.
  • Verify after any change: reset state (delete backend/data, out, archive; seed returns on boot), then npm run smoke → 23/23. On stale state the idempotency check reports 200 instead of 202. Only one instance can bind port 3000 — a stale process holds old code and old in-memory state.

Knowledge check — Track B

Answer before expanding.
1. Your Kafka consumer redelivers a trigger message. What reaches the customer, and how do you detect it happened?

Exactly one communication. Both deliveries carry the same business-derived idempotency key; the second call returns HTTP 200 with "replayed": true and the original transaction_id (FR-2.3) — no new composition, no new dispatch. Alert on unexpected replay rates, not individual replays.

2. Operations must re-mail one customer from last night's 50k-document run. Walk the exact steps.

Find the customer's entry in the run's report file (FR-3.5) — it carries recordIndex and the fromPage/toPage sheet range — then POST /batch/{jobId}/reprint with that index (FR-3.6). You get a standalone print-ready file; the reprint lands in the audit trail.

3. Why did the driver file's "jane doe" render as "Jane Doe" without any change to template or batch code?

The pre_ingestion lifecycle hook (FR-13.2) title-cased names before composition saw the records. It is sandboxed, quota-bound, versioned per application, and logs its own events — extension without touching core services.

4. A do-not-contact check must apply to every template and channel. Where does it go?

A pre-dispatch hook (FR-13.2). It is delivery policy, not content: one hook covers the whole application, versioned and audited independently of any layout.

Knowledge check — Track C

Answer before expanding.
1. A customer disputes an interest rate from a letter sent 14 months ago. What is your evidence chain?

Retrieve the archived copy via the index (FR-5.1) and check its stored content hash; recompute the ledger hash from the stored template version + the claimed payload (FR-6.2) — a match proves the archive is what was composed; the FR-6.1 chain (gateway handshake + delivered) proves it reached them. Three artifacts, all captured in this track.

2. Why is the failed email attempt still visible after the SMS fallback succeeded — and why do you want it that way?

Each attempt writes immutable events into the same transaction (C1's JSON shows Failed with reason and timestamp). Failover adds attempts; it never rewrites. For you, the failure is the audit record — it proves the preferred-channel obligation was attempted and why the fallback engaged.

3. The ledger stores no document copy. Why is a hash of template-version + payload sufficient?

Composition is deterministic: same approved template version + same canonical payload reproduces the same document. The sealed hash pins those inputs immutably, so integrity is verifiable without duplicating massive storage — the PRD's explicit design intent. C2 shows a single changed field diverging the hash.

4. What sealed the ledger — the delivery or the composition — and why does the difference matter?

Composition (sealedAt matches the Composed event in C1, before any gateway contact). This means content integrity is fixed before delivery vagaries begin: a failed or failed-over delivery cannot alter what was composed.

Knowledge check — Track D

Answer before expanding.
1. Why can't you edit the compliance footer, even though it's right there on your page?

It belongs to the shell — a locked block (FR-1.3) owned by designer/compliance roles and enforced by the server (Track A proved it with a real 403). That guarantee is what lets you send quickly: reviewers only need to read your zones.

2. What stops AI Draft from inventing a discount the bank never approved?

FR-7.1 grounding: drafting retrieves only from the approved paragraph library, and the response names its sources ("grounded in: …"). Ungrounded generation into customer communications is prohibited by the PRD (§3.7) — an architectural rule, not a model setting.

3. Your letter is urgent — can you skip approval by printing it locally?

No, by design. Governed dispatch is the only exit; it applies approval when policy requires and always records track & trace (your send in D5 produced a transaction and audit URL instantly). Urgency is handled in the approval routing configuration, not by bypassing it.
